# V5.1 correction delivery

Prepared on the existing `codex/ui-ux-rebuild-october-2026` feature checkout. Earlier V5 and Urban Adventure changes remain in place. No production writes, deployments, commits, pushes, or migrations were performed.

## A. Implemented locally

- Shared discovery location, explicit Apply location and Use My Location, provider-capability mode selection, default Drive/20 minutes and seven discrete limits: 5, 10, 15, 20, 30, 45, 60.
- All four modes use actual origin-to-venue routed durations to exclude over-limit or unknown journeys. Preferences never delete itinerary selections. The legacy draft radius is retained only for draft compatibility and is not used for journey estimates.
- Venue duration badges and separate estimates between consecutive itinerary stops. These are not a total-route budget, traffic forecast, future transit timetable, or opening-hours claim.
- Explicitly consented, labelled straight-line distance fallback. This disables the journey-time limit and never converts kilometres into minutes. Consent resets when the origin or travel mode changes.
- Discovery debounce of 650 ms and itinerary debounce of 800 ms. Account-scoped in-memory five-minute success cache, thirty-second failed-result cache, concurrent identical request coalescing, maximum 500 entries. Slider thresholds do not trigger routing requests.
- Matrix batches of 25. Discovery checks up to 50 matching candidates; search/category/collection refinement happens before the bound. Consecutive itinerary legs use at most five cached one-element calls after order settles.
- The existing authenticated Google Distance Matrix function accepts validated driving/walking/transit modes, validates coordinates and durations, rejects over-large requests, excludes imprecise venue geocodes, applies upstream timeouts and fails closed on quota failure. Old deployments expose driving only; mismatched mode responses are rejected. Address-only venue estimates require the new handler's coordinate/origin verification flags; an older handler can still route known stored coordinates without passing off a suburb centre as a venue.
- A new authenticated `discover-venues` function reuses the existing server-held Google Maps key and Places Text Search (New). It returns up to twenty deduplicated provider records with identifiers, names, addresses, coordinates, classifications and attributions. No model-generated venue records are accepted.
- AI Finds searches new external records, excludes already-saved identifiers/name-address pairs, optionally ranks verified records using the existing AI service, and provides independent Save to library and Add to itinerary actions. Provider failure has an explicit unavailable state without a saved-only substitute. Category preferences filter the real records. Availability, dietary suitability and budget are not guaranteed.
- Randomise My Plan previews a varied saved-only plan or requested category mix. Merge/Replace/Keep current are explicit actions; six stops and duplicate guards remain. Shortfalls explain how to refine preferences or travel limit.
- Touch drag handles through the existing Framer Motion dependency, pointer drag feedback and keyboard Arrow/Home/End fallback. Reordering keeps chronological time slots while moving venues through them. Draft state and same-event edits use the same order.
- Generic Alex Taylor / alex.taylor placeholders only. Discovery owns the location inputs; Event Details contains only event name, date and timing.
- Evidence-backed multiple category tags: Bar alone is not Nightlife; provider Bar + live-music/nightclub evidence can match both. Outdoors and indoor Activity remain separate.

## C. Blocked or unverified

- No live routing/Places success claim: functions were not deployed and production provider credentials, billing, restrictions, quotas and API enablement were not inspected or changed.
- The new endpoint and revised routing handler need approval before deployment. Until then, external discovery clearly reports unavailable; an older routing deployment safely provides driving only. Missing routes are never guessed.
- Google Distance Matrix is the application's existing **legacy** provider integration. Its availability for this project must be checked in staging; migration to Routes API is a separate decision if needed.
- Transit estimates use the provider's current departure-time context, not the planned event date/time. Live traffic is not requested. Provider coverage may vary by region.
- Discovery is a bounded candidate search, not an exhaustive city-wide isochrone search. Broader libraries can be refined by search, category or collection. External search returns at most twenty candidates per explicit search.
- Travel preferences/routes are draft-level and are not added to the confirmed-event database schema. Historical event stops without stored coordinates are geocoded from their stored addresses for leg estimates. Failed lookups show unavailable.
- Native phone touch/autoscroll, physical Android/Capacitor, real browser geolocation permissions and live OAuth remain untested. Pointer drag was verified at a 390 × 844 viewport; granted/denied location callbacks were verified in component tests.
- Existing event writes are sequential rather than transactional; partial network failures remain a pre-existing persistence risk. Confirmation retries preserve the pending ID and ambiguous writes require review.
- Existing six-stop-all-accounts and optional-end-time SQL proposals remain **unapplied**. Client capability guards still protect older production limits; this correction does not certify those backend capabilities are enabled.

## F. Database and release prerequisites

No migrations proposed or applied for V5.1. Reuses saved_venues, plans, stops, the existing app_secrets Google key lookup and consume_rate_limit RPC. No key values were printed or packaged. No production settings were changed.

Approval is required before any production deployment. First verify in staging:

1. Existing Google key access to Distance Matrix, Geocoding and Places API (New), project billing and restrictions; do not introduce a new paid provider.
2. Deploy the reviewed `travel-times` and `discover-venues` changes only after approval, retaining JWT verification and internal end-user authentication.
3. Rate enforcement is available. Existing route cap is 60 authenticated requests/hour/user with at most 100 destinations/request; discovery is 20 requests/hour/user, 20 Places results each. Client bounds are tighter. Set provider project budgets/quota ceilings deliberately; these are not global spend guarantees, and retries/leg lookups also consume requests.
4. Review provider attribution and storage terms for the intended production saving workflow. Cards show Google Maps text/link and available third-party attributions. This implementation does not claim a legal compliance audit.
5. Run staging real-provider travel, mode coverage, unavailable/quota cases, Google login, owner edits/guest RSVP, plus physical touch/Android tests. The older six-stop/end-time proposals need their own schema review and explicit approval.
